# QControl API — Business Feature Blocks

## 0. القواعد العامة لكل الـAPI

معظم الـEndpoints الإدارية تعمل بالنمط:

```text
Controller
→ MediatR Command / Query
→ Handler
→ Repository / Domain
→ Result<T>
→ ToIActionResult()
→ ProblemDetails on failure
```

الـAuthorization يعتمد على:

```text
[Authorize]
[Permission("...")]
```

والـRuntime الخاص بالـ`Ticket/Reservation/Kiosk` يضيف أيضًا:

```text
TicketRuntimeRequestGuard
→ authenticated user
→ branch access
→ performerId
```

الـ`RowVersion` تستخدم في العمليات التي تحتاج `Optimistic Concurrency`.

---

# Block 1 — Authentication

## Business Capability

إدارة دخول المستخدم وإجباره على تغيير الـTemporary Password في أول Login.

---

### 1. Login

```http
POST /api/auth/login
```

**Request**

```json
{
  "userNameOrEmail": "admin@example.com",
  "password": "******"
}
```

**Response**

```text
UserTokenDto
```

وتحتوي على بيانات الـJWT والـroles والـpermissions والـbranch context ومعلومات password lifecycle.

**Validation**

* `UserNameOrEmail` مطلوب.
* Max length = 200.
* `Password` مطلوبة.
* Max length = 200.
* بيانات الدخول الخاطئة → `Unauthorized`.

**Business Capability**

Authentication + بناء Authorization context للمستخدم.

**Outcome**

JWT صالح للاستخدام في باقي الـAPI.

**Value**

بوابة الوصول لكل الـAdministrative/Operational APIs.

---

### 2. Change Initial Password

```http
POST /api/auth/change-initial-password
```

**Authorization**

```text
Authenticated
```

**Request**

```json
{
  "newPassword": "..."
}
```

**Validation / Business**

* الـToken لازم يكون خاص بسيناريو تغيير أول Password.
* المستخدم `IsFirstLogin = true`.
* المستخدم Active.
* الـpassword الجديدة تحقق Password Policy.
* لا تكون نفس الـTemporary Password.

**Outcome**

تغيير الـPassword وإصدار Token جديدة بدون `passwordChangeRequired`.

# [FE][Kiosk] Implement Customer Ticket Issuance Flow – Service Selection, Reservation Lookup & Direct Ticket

## الهدف

### Impact on Frontend

الـFrontend حاليًا لا تستطيع معرفة من نفس Kiosk response هل الخدمة تدعم:

```text

```

### Required Backend Decision

```json

داخل كل `Leaf Service` في Kiosk service discovery response.

حتى يصبح الـFrontend flow:

hasReservation = false
→ Show:
   - تذكرة جديدة فقط
```

حتى يتم تعديل الـBackend، لا يجب على الـFrontend Hardcode هذه القاعدة.

# 95. Acceptance Criteria

تعتبر الـFrontend task مكتملة عندما:

```text
✓ Kiosk loads Branch Branding dynamically.

✓ Kiosk uses returned Service Tree.

✓ Language behavior follows Branch configuration.

✓ Only selectable Leaf Services can complete customer flow.

✓ Service Custom Inputs are rendered dynamically.

✓ String/Integer input constraints are supported.

✓ Reservation lookup supports one Custom Input minimum.

✓ Reservation lookup supports multiple Custom Inputs.

✓ Search does not require all isRequired fields.

✓ Multiple search inputs are sent together.

✓ Search handles Field mode for services without Custom Inputs.

✓ Reservation search results show multiple matching reservations.

✓ Reservation status is displayed.

✓ Customer explicitly selects Reservation.

✓ Selected Reservation is converted using Kiosk conversion endpoint.

✓ New Ticket flow creates Ticket directly.

✓ New Ticket does not create Reservation.

✓ Required Custom Inputs are enforced on Direct Ticket flow.

✓ Field is required on Direct Ticket when Service has no Custom Inputs.

✓ TicketDetailsResponse is used after successful issuance.

✓ Ticket number is displayed prominently.

✓ Printer flow starts only after successful ticket creation.

✓ No ticket is printed when Backend returns failure.

✓ Double submit is prevented.

✓ POST create operations are not blindly auto-retried.

✓ API localized error messages are displayed.

✓ Kiosk state is cleared after successful completion.

✓ SegmentId is never hardcoded.

✓ Authentication credentials are never hardcoded.

✓ Frontend does not recreate Backend quota/numbering/workflow logic.
```
